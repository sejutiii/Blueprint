FUTURE EXTENSIONS
=================

1. Split light/heavy tier LLM providers
   Currently: user picks one provider for all agents.
   Future: let user configure two providers separately —
   a fast/cheap model for light tasks (diff summarization, keyword extraction, ADR drafting)
   and a more capable model for heavy tasks (compliance checking, extension detection, ARCH.md generation).
   The LLMClient already has a `tier` parameter placeholder for this.

2. Neural embeddings for the Retrieval Agent
   DONE (superseded this note): RetrievalAgent now blends TF-IDF cosine similarity with
   local sentence embeddings (Xenova/all-MiniLM-L6-v2, 384-dim, run in-process via
   @huggingface/transformers / ONNX — no API key, no network call per query). Falls back
   to TF-IDF-only if the local model fails to load. Embeddings are cached per ADR in
   .blueprint/adr-index.json (ADR.embedding) so they're only computed once.
   Possible future: swap the local model for Gemini's text-embedding-004 API for
   potentially higher-quality semantic retrieval. Trade-off to weigh before switching:
   loses offline capability and adds a per-query network call + API cost, and ties
   retrieval quality to whichever provider the developer configured (Anthropic and Groq
   don't offer embedding APIs, so this would need a fallback to the local model anyway
   for those providers).

3. ARCH.md as a living document
   Currently: ARCH.md is written once on init and updated only when a new component is
   confirmed via compliance review (extension detection). The Constraints and Open Questions
   sections go stale after constraint elicitation adds ADRs.
   Future: ARCH.md should always reflect the current state of the codebase. This means:
   - After constraint elicitation, sync confirmed constraints back into arch.json and re-render ARCH.md.
   - Provide a "Regenerate ARCH.md from codebase" command that re-analyzes the project
     and rewrites the architecture document (components, constraints, data flow) to match reality.
   - Consider hooking into file save/commit events to prompt a refresh when significant
     structural changes are detected.

4. Non-git diff support
   Currently: DiffSummarizer runs `git diff --cached` and `git diff` — requires the workspace
   to be a git repository with at least one commit. Projects without git get an empty diff
   and the "No uncommitted changes" screen regardless of actual file state.
   Future: detect whether the workspace is a git repo first. If not, fall back to a
   snapshot-based approach — save a file manifest (paths + hashes) on init, then diff
   the current file state against that snapshot when the user runs a compliance review.
   This would allow BluePrint to work on brand-new projects that haven't been committed yet.
